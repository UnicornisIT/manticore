# Обновления Manticore Desktop для Windows

## Архитектура и прежняя проблема

Desktop — Python 3.11, pywebview/WebView2, PyInstaller one-file EXE и Inno Setup 6 x64. Основной процесс и узкий JS API находятся в `desktop/windows_client.py`. Renderer — Flask/Jinja и обычный JavaScript. Electron, preload, Node integration, electron-builder и electron-updater здесь отсутствуют. У pywebview нет штатного Windows autoUpdater, поэтому доработаны существующие Python-загрузчик и Inno Setup, без второго механизма установки. Рекомендация pywebview по упаковке: https://pywebview.flowrl.com/guide/freezing.html.

Раньше клиент сначала обращался к серверу Manticore за административным разрешением конкретного релиза, требовал Immutable Release и обязательный сертификат. Проверка при старте блокировала запуск; скачивание и установка были одним действием, без прогресса в UI. Несовпадение разрешения, отсутствие сертификата или изменяемый релиз блокировали обновление. Старые серверные endpoints административного разрешения сохранены для совместимости со старыми клиентами, но новый Desktop ими не пользуется.

## Источник и версии

Источник — публичный GitHub Releases репозитория `UnicornisIT/manticore`. PAT не нужен и нигде в клиенте не хранится. Сохранённый `update_server_url` больше не управляет Desktop-обновлениями.

Начиная с `0.0.5-alpha`, в настройках доступны две независимые карточки: слева «Стабильные обновления», справа «Тестовые обновления». На узких экранах карточки идут одна под другой. Каждая показывает свой статус, проверку, скачивание с прогрессом и отдельное действие установки. Пользователь может проверить любой канал независимо от установленной версии; установка более старой или равной версии запрещена.

Оба канала читают `/releases?per_page=100&page=N`, пропускают черновики и теги вне SemVer, выбирают максимальную версию внутри своего канала. Стабильный канал допускает только версии без предварительного суффикса и без флага prerelease. Тестовый канал допускает только версии с предварительным суффиксом или флагом prerelease. Поэтому ошибочно назначенный Latest с alpha-тегом больше не вызывает ошибку в стабильной карточке. Если подходящего нового выпуска нет, карточка сообщает «Новых обновлений нет». Повреждённые метаданные кандидата и сетевые ошибки по-прежнему отображаются как ошибки.

Просматриваются страницы по 100 релизов, максимум 10 страниц; если последняя страница заполнена, проверка прекращается с сообщением о лимите. Фоновая проверка при запуске выбирает канал по установленной версии (`preview` для alpha/beta/rc, `stable` для стабильной версии). В настройках оба канала остаются доступны вручную.

В обоих каналах кандидат обязан содержать ровно один установщик подходящей версии, допустимый размер и SHA-256 digest GitHub. Ссылка должна точно соответствовать официальному репозиторию, тегу и имени EXE по HTTPS. Ошибка проверки самого нового кандидата отображается пользователю без скрытого отката к более старому релизу. Проверки целостности скачанного файла и подписи согласно встроенной политике доверия действуют в обоих каналах.

Версия сравнивается по SemVer: числовые major/minor/patch, правила числовых prerelease identifiers, build metadata не влияет на приоритет. Равная и более старая версия не устанавливаются. Можно перейти напрямую с 1.0.0 на 1.5.0.

Единственный источник версии — `VERSION`. Из него берутся версия Python/интерфейса, PE FileVersion/ProductVersion EXE, версия и имя установщика, metadata. CI требует точное совпадение тега `v<VERSION>` с `VERSION`; предварительные теги публикуются только как prerelease с latest=false. Текущее значение VERSION не повышается автоматически.

API GitHub Releases: https://docs.github.com/en/rest/releases/releases#get-the-latest-release.

## Состояния и IPC

`DesktopApi` предоставляет `get_update_channels()` для получения обоих статусов и `get_update_status(channel)`, `check_for_update(channel)`, `download_update(channel)`, `install_approved_update(channel)` для работы с выбранной карточкой. Допустимы только `stable` и `preview`; вызовы без аргумента сохранены для фоновой проверки и совместимости. Метод `install_approved_update` сохраняет прежнее имя, но устанавливает **только уже скачанный** файл. Аргументы URL, пути EXE и команды от JavaScript не принимаются. Статус содержит версию, текст заметок, ошибку и числовой прогресс; путь установщика и политика доверия не передаются renderer.

Последовательность: idle → checking → available/current → downloading → downloaded → installing. Ошибки переходят в error; повторная проверка восстанавливает процесс. Параллельные операции одного канала объединяются/отклоняются под lock. Каналы хранят отдельные манифесты и файлы; общая блокировка API исключает запуск второго установщика во время установки из другой карточки. Проверка и скачивание работают в фоновых потоках. Установка требует отдельного клика и нативного подтверждения; отмена оставляет файл готовым к установке.

После запуска окна выполняется одна отложенная проверка (4 секунды), без автоматического скачивания. `--skip-update` пропускает её. JavaScript опрашивает только локальный IPC во время операции и короткого стартового окна; регулярного опроса GitHub нет. В обычном браузере updater отсутствует, в Python dev-запуске показано, что нужна установленная Desktop-сборка.

`static/js/desktop-updater.js` также встроен в Desktop и подключается к загруженным страницам доверенного origin. Это сохраняет уведомление и управление обновлением при подключении к более старому серверу Manticore. Заметки релиза выводятся через textContent. Политики CSP/WebView2 не ослабляются.

## Скачивание, подпись и установка

Используется существующий потоковый Python-загрузчик. Перед загрузкой проверяется запас свободного места; контролируются опубликованный и максимальный размер, затем SHA-256. Частичный или повреждённый файл удаляется. Перед запуском установщика файл проверяется повторно.

Подписанная сборка закрепляет SHA-256 сертификата издателя и требует соответствующую Authenticode-подпись обновления. Сборка без сертификата явно включает `allow_unsigned_updates` в **встроенной** политике; HTTPS официального GitHub и проверка digest остаются обязательными. Отсутствующая или повреждённая политика не включает unsigned автоматически. Нельзя изменить источник или отменить подпись через сервер/renderer.

Установщик сохраняется в `%LOCALAPPDATA%\Manticore\updates`. Отдельный скрытый PowerShell-процесс ожидает завершения клиента и родительского PyInstaller bootloader (с таймаутом), запускает Inno Setup с нужными `/DIR`, scope, `/NORESTART`, `/CLOSEAPPLICATIONS`, `/NORESTARTAPPLICATIONS`, `/LOG`, ожидает его завершения, записывает результат и запускает приложение с `--skip-update`. Windows целиком не перезагружается. Inno `[Run]` имеет `skipifsilent`, поэтому двойного запуска нет. При отмене UAC/ошибке установки повторно открывается имеющееся приложение и отображает ошибку из результата. Если EXE заблокирован Windows и не запускается вообще, результат остаётся на диске для диагностики.

Локальный backend завершается при закрытии окна. Идентификатор приложения и mutex постоянны между релизами. Scope определяется по зарегистрированному пути текущей установки, чтобы не перепутать одновременно установленные per-user/all-users копии.

## Данные пользователя

Конфигурация (`desktop-config.json`), секрет локальной сессии, стандартная БД, профиль WebView2, предпочтения и логи расположены в `%LOCALAPPDATA%\Manticore`, отдельно от `%LOCALAPPDATA%\Programs\Manticore`. Пользовательская БД по выбранному пути сохраняется. Inno заменяет EXE/иконки и удаляет только старые программные ресурсы `_internal`; БД, настройки и профиль не входят в список удаления. Updater не выполняет SQL и не переносит пользовательские данные. Для изменений схемы БД релиз обязан сохранять совместимость миграций приложения и резервное копирование.

## Release assets

Каждый стабильный релиз содержит:

- `Manticore-Setup-X.Y.Z.exe` — полный Windows x64 installer;
- `desktop-update.json` — schema_version, repository, version, tag, asset, size и SHA-256;
- `SHA256SUMS.txt` — контрольная сумма установщика.

Авторитетные metadata для клиента — GitHub Releases API (включая asset digest). JSON и SHA256SUMS публикуются для проверки сборки/диагностики; клиент не доверяет альтернативному URL из metadata. `latest.yml` и blockmap не нужны для PyInstaller/Inno Setup. Отсутствие EXE или digest — явная ошибка, а не отсутствие обновлений.

## Как выпустить версию

1. Изменить `VERSION` на стабильную версию, например `1.3.0`.
2. Проверить изменения и выполнить тесты.
3. Закоммитить; создать `git tag v1.3.0` и отправить `git push origin v1.3.0`.
4. Дождаться workflow `Windows desktop release`.
5. Проверить Latest, assets, digest и обновление установленного клиента.

CI: checkout → Python 3.11 + Node 22 (для JS-тестов) → проверка тега → pip по `requirements-desktop.lock` → pip check → Python/JS syntax checks → все unittest, включая frontend regressions → Inno Setup → необязательная подпись → PyInstaller и installer → metadata → provenance attestation → artifact → draft Release → загрузка всех assets → сверка размера/digest через GitHub API → публикация stable Latest.

Публикация не производится, если версии расходятся или проверки не прошли. Повторный запуск может закончить **draft**, но не перезаписывает опубликованный релиз: для него требуется новая версия. Рекомендуется включить GitHub immutable releases, чтобы после публикации assets не менялись. Private repository без анонимного доступа к Releases этой схемой не поддерживается; токен в клиент для обхода не добавлять.

В проекте нет package.json, npm/pnpm/yarn, отдельных lint/typecheck/Web-build команд. Flask-шаблоны и static входят в Desktop bundle, тестируются существующими тестами. Syntax checks не следует выдавать за полноценные lint/typecheck. Lockfile фиксирует Python-зависимости; обновлять его в Windows Python 3.11 после проверки совместимости. Воспроизводимый набор зависимостей не означает побитово одинаковые подписанные бинарники.

Локальная сборка: `./build_windows_desktop.ps1`. С готовым окружением — `-SkipDependencies`. `-SkipInstaller` собирает только EXE. Старый флаг `-UnsignedDevelopmentBuild` оставлен совместимым; отсутствие сертификата теперь не выключает updater. Результат в `dist/installer`; компиляция установщика сначала выполняется в отдельной staging-папке, затем готовый файл заменяет итоговый.

## Windows code signing

В GitHub repository secrets подключить `WINDOWS_CERTIFICATE_BASE64` (PFX с приватным ключом) и `WINDOWS_CERTIFICATE_PASSWORD`. Для публичного распространения рекомендуется доверенный Windows code-signing сертификат. CI импортирует его только на runner, подписывает EXE/installer через Windows SDK signtool с timestamp, проверяет подпись и удаляет сертификат/PFX. Без обоих secrets собирается unsigned-вариант; неполная конфигурация должна быть исправлена. Сертификаты, пароли и токены не коммитить.

Локально: `./build_windows_desktop.ps1 -CertificateThumbprint <thumbprint>`. Сертификат должен быть доступен signtool в хранилище Windows. После перехода на подписанные сборки сохраняйте сертификат для следующего релиза: клиенты закрепляют его fingerprint. Ротация требует заранее подготовленного переходного релиза, доверяющего новому сертификату и подписанного старым; простая замена CI secrets для уже закреплённых клиентов не подходит.

## Проверка обновления и логи

Основной набор: `.venv/Scripts/python.exe -m unittest discover -s tests -v`. Он проверяет SemVer, версии через несколько выпусков, draft/alpha/beta/rc, ошибки API, checksum/размер, недостаток места, прогресс, сериализацию, подтверждение, tampering и подпись, UI и существующие функции приложения.

Полный production E2E выполняется на отдельной Windows VM: установить подписанную/unsigned версию A, создать тестовые настройки/записи БД, выпустить стабильную B>A обычным workflow, в A проверить уведомление → скачать → убедиться в прогрессе/готовности → подтвердить установку → увидеть B после перезапуска и проверить данные. Повторить отказ сети, отмену подтверждения/UAC, равную/более старую Latest. Не публикуйте фиктивные stable-релизы ради теста; draft не должен обнаруживаться production-клиентом.

Локальная безопасная альтернатива: отдельная копия исходников в `build/updater-validation`, отдельные AppId/mutex/APP_NAME, версии 1.0.0 и 1.5.0 только в этой копии. Собрать настоящие PyInstaller/Inno артефакты, установить в тестовую папку с отдельными данными, проверить замену и запуск. Источник GitHub проверять отдельно контрактными тестами/публичным API. Такая проверка не равна полному E2E из опубликованного GitHub Release.

Логи: `%LOCALAPPDATA%\Manticore\logs\client.log` (кнопка «Открыть журнал»), `logs\installer.log`, `updates\install-result.json` до его обработки следующим запуском. Ищите `[Updater]`: текущая версия, проверка, кандидат, прогресс, проверка файла, установка, перезапуск. Учётные данные в updater logs не записываются.

## Выпуск 0.0.2-alpha

Для предварительных выпусков workflow проверяет точное совпадение тега и VERSION с явно разрешённым prerelease. Тег `v0.0.2-alpha` публикуется с `prerelease=true` и `latest=false`; стабильный канал Desktop продолжает игнорировать alpha/beta/rc, а предварительный канал предлагает их как обновления. Старый клиент без поддержки предварительного канала нужно один раз обновить вручную установщиком новой сборки. Стабильные теги `vX.Y.Z` по-прежнему публикуются как stable Latest.

## Проверка подписи в CI

После подписи workflow выводит Authenticode Status/StatusMessage и запускает `desktop/release_tools.py --verify-signatures`. Проверяются оба файла: EXE приложения и installer. Используется тот же verifier, что в Desktop: точное совпадение SHA-256 закреплённого сертификата и WinVerifyTrust. Недоверенный корень (`0x800B0109`) допускается только при совпавшем fingerprint; это поддерживает закреплённый самоподписанный сертификат без добавления его в Root store runner. Любой другой код ошибки, отсутствие подписи, другой сертификат или отсутствие ожидаемого файла останавливают выпуск. Отсутствующий pin не превращает этот шаг в unsigned-проверку. Такой сертификат не становится автоматически доверенным Windows/SmartScreen.

В логах запуска `logs_92281299240.zip` сборка и signtool завершились успешно, а старый CI остановился на проверке `Status == Valid`. Точный StatusMessage тогда не выводился, поэтому недоверенный корень является возможной, но не доказанной причиной этого конкретного запуска.
