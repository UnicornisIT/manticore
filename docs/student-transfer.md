# Ручной перевод студента: реализация и проверка

## Поведение и архитектура

1. Раньше административный POST обработчик запрещал перевод при count >= 25, а select отключал полные группы. Проверка количества выполнялась до получения блокировки записи. Обычное редактирование cohort1 позволяло обходить процедуру перевода.
2. Источник заполненности сохранён: get_group_student_count считает записи students по cohort1. Общий лимит — MAX_GROUP_STUDENTS = 25. Счётчики не денормализуются и не обрезаются.
3. Основная сервисная операция — transfer_student_to_group в app.py, отдельно от HTTP обработчика transfer_student_group. Она рассчитана на одного студента и может быть использована будущим массовым сценарием; массовый перевод не добавлен.
4. Существующее право — role=admin. Другие роли не могут выполнять ручной перевод, включая переполнение; новой системы ролей нет. Право проверяется маршрутом и сервисом.
5. Интерфейс сначала запрашивает серверный preview. Полная либо переполненная цель возвращает HTTP 409 и code=capacity_exceeded с фактическими количествами. Только подтверждение «Перевести всё равно» отправляет capacity_override=true. Обычный перевод также подтверждается.
6. BEGIN IMMEDIATE выполняется перед загрузкой студента, групп и количеств. Два писателя SQLite сериализуются. После preview операция снова читает фактическую заполненность под блокировкой; занятое последнее место вызывает новый диалог. expected_source защищает от перевода студента, чья группа уже изменилась, и от повторного сохранения того же запроса. Ошибка блокировки возвращает concurrent_update.
7. cohort1 и cohort2 обновляются вместе. cohort2 вычисляется существующим get_student_course_group / derive_cohort2; при выключенных глобальных группах записывается пустое значение. Сохранение обычной карточки больше не обновляет эти поля.
8. Группа назначения должна существовать, быть видимой и относиться к кампании текущей группы. Изменение специальности и образовательной базы было разрешено существующим ручным сценарием и осталось разрешено, но серверный preview предупреждает об обоих изменениях. Если обязательный mapping глобальной группы отсутствует, перевод отклоняется. Совместимые группы сортируются первыми, затем по заполненности.
9. История student_group_transfers и audit_logs записываются в той же транзакции, что и студент. Аудит содержит оператора, student username, старые/новые группы, количества до/после, лимит, переполнение, override, приказ и необязательный комментарий. Время хранится существующим механизмом аудита. Пароль студента не включается.
10. PDF остаётся необязательным и проходит существующую проверку загрузки. При ошибке записи/commit БД откатывается, сохранённый PDF удаляется. Ошибки БД не раскрывают traceback пользователю.
11. Manticore готовит локальные данные для Moodle и выгрузок; прямой синхронизации Moodle в этом сценарии нет. Новых внешних вызовов и очередей не добавлено. Экспорт получает обновлённые cohort1/cohort2 из students.
12. Существующее автоматическое распределение и его проверки MAX_GROUP_STUDENTS не изменены. Флаг ручного override в автоматические алгоритмы не передаётся. Другие студенты при переводе не перемещаются.

## Интерфейс

В select и таблице групп показывается фактическое количество:

- count < capacity: например 12/25;
- count == capacity: 25/25 · заполнена (warning в таблице);
- count > capacity: 26/25 · переполнена (danger в таблице).

Текущая группа отключена; заполненные доступны. Подтверждение показывает обе группы до/после и предупреждения о совместимости. Используется существующий modal Manticore, с Escape, удержанием Tab и восстановлением фокуса. Добавлен Promise API ManticoreConfirm для серверных подтверждений. После успеха карточка автоматически открывается с обновлёнными группами, историей и уведомлением. В этом экране нет progress bar, поэтому ширина более 100% не возникает.

## Изменённые файлы этой задачи

- app.py — сервис, HTTP протокол, статусы заполненности, сортировка и защита обычного редактирования.
- templates/edit_student.html — заполненность, комментарий, readonly текущая группа, подключение JS.
- static/js/student-transfer.js — preview, подтверждение, override, обработка ошибок и повторного submit.
- static/js/modern-ui.js — использование существующего диалога из JS, управление фокусом.
- templates/add_group.html и static/css/pages/add_group.css — заполненная/переполненная группа.
- tests/test_app.py — серверные проверки и адаптация текста существующего success теста.
- tests/frontend/student_transfer.test.cjs и tests/test_student_transfer_frontend.py — протокол подтверждения.
- README.md и docs/student-transfer.md — документация.

Другие изменения, уже находившиеся в рабочей копии до задачи, сохранены.

## Проверки

Добавлены серверные сценарии: четыре сочетания полной/неполной исходной и целевой групп; полная и переполненная цель без override и с override; actual capacity после preview; смена исходной группы; два настоящих параллельных SQLite писателя на последнее место; та же группа; чужая кампания; неизвестная группа; отсутствие прав; откат студента/истории/PDF при ошибке аудита; невозможность обхода через обычное редактирование. Проверяются глобальная группа, аудит и реальные количества.

Четыре Node теста проверяют отмену без override, явное подтверждение, повторное подтверждение при занятом последнем месте и отсутствие повторной отправки после concurrent_update.

В браузере на изолированной SQLite базе вручную проверены перевод в полную группу, последующий перевод в свободную, новая глобальная группа, история, success notification, таблица 26/25, DARK/LIGHT, Escape, Tab и возврат фокуса. Настоящий Desktop/WebView2 не запускался: доступны браузерные поверхности, native управление в этой сессии отключено. Поэтому Desktop приёмка остаётся непроверенной, хотя существующие автоматические тесты desktop входят в общий набор.

Финальный полный прогон: `.venv\Scripts\python.exe -m unittest discover -s tests` — **127 тестов, OK**, 65.866 секунд. Включены существующие migration/allocation/enrollment/order/capacity и desktop тесты. Протокол фронтенда содержит ещё 4 Node subtests внутри Python wrapper. `node --check` для обоих изменённых JS — успешно. `git diff --check` — exit 0, ошибок нет.
