# Практические границы безопасности

## Учётные данные

Пароли пользователей Manticore хранятся только как Werkzeug-хеши. Начальный администратор создаётся с флагом обязательной смены пароля; до успешной смены доступны только сама форма смены и выход. Установочные скрипты не выводят пароль в консольный transcript или журнал.

Поле `students.password` существует только для совместимости с Moodle CSV/XLSX. Единственное допустимое значение — константа `cron`. Значение из загруженного файла и формы редактирования игнорируется; при запуске старые значения в `students` и `students_duplicates` заменяются заглушкой. Manticore не является хранилищем реальных паролей Moodle.

Миграция схемы 5 сначала заменяет старые значения, затем создаёт SQLite-триггеры, которые отклоняют любое новое непустое значение кроме заглушки до записи в таблицу или WAL. `NULL` безопасно нормализуется до заглушки. Это защищает и от будущего обхода прикладного импортера прямым SQL-кодом.

## Сетевой доступ

Встроенный Flask HTTP-сервер допустим только на loopback. Если `APP_HOST` открывает сетевой интерфейс, приложение журналирует предупреждение. Для любого доступа с другого компьютера обязательны HTTPS reverse proxy или доверенный VPN, `SESSION_COOKIE_SECURE=true` и выключенный debug. Пример TLS-конфигурации находится в `deploy/nginx-https.example.conf`.

## Обновления

Административная кнопка запускает только заранее определённую systemd-службу с валидированным именем и без пользовательских аргументов. Updater принимает релизы только из `UnicornisIT/manticore`, проверяет строгий SemVer-тег и выполняет только fast-forward до тега. Остаточный риск: серверные Git-теги не требуют криптографической подписи, поэтому компрометация GitHub-аккаунта или репозитория остаётся доверенной границей. Рекомендуемый следующий шаг — обязательная проверка подписанных тегов или attestations перед переключением кода.

Desktop закрепляет официальный репозиторий, URL/размер/SHA-256 asset и, для подписанных сборок, SHA-256 сертификата Authenticode. SHA-256 из того же Release не аутентифицирует издателя unsigned-сборки; подробности и точка расширения для отделённой подписи описаны в `docs/desktop-updates.md`.

## Резервные копии

SQLite-копии создаются через backup API и проходят проверку целостности. Новые файлы получают owner-only режим, где это поддерживает файловая система. Срок хранения задаёт `BACKUP_RETENTION_DAYS` (по умолчанию 30 дней); очистка выполняется после создания новой копии. На Windows/сетевых хранилищах администратор обязан отдельно ограничить ACL каталога. Встроенного шифрования бэкапов нет: для внешнего носителя используйте шифрование тома или зашифрованный архив с отдельным управлением ключами.

## Проверка зависимостей

CI запускает `pip-audit` отдельно для `requirements-prod.lock` и `requirements-desktop.lock`. Найденные уязвимости должны блокировать выпуск до обновления зависимости либо документированного временного исключения с владельцем и сроком устранения.
