# Обновление приложения

## Единый механизм

`update_app.py` — каноническая реализация серверного обновления. Корневые
`update.sh`, `update_windows.ps1`, `update_windows.bat` и
`update_and_run_windows.bat` являются совместимыми обёртками над скриптами в
`scripts/`; отдельную логику обновления в них добавлять не следует.

Linux:

```bash
./update.sh /srv/manticore
```

Windows PowerShell:

```powershell
.\update_windows.ps1
```

Перед изменением кода updater создаёт и проверяет SQLite-бэкап, если база
существует. Локальные `.env`, база и загрузки не заменяются.

## Модель доверия

Updater принимает релизы только из закреплённого репозитория
`UnicornisIT/manticore`, проверяет строгий SemVer и разрешает только
fast-forward к выбранному тегу. Это предотвращает случайный переход на
произвольную ветку, но тег пока не обязан иметь криптографическую подпись.
Компрометация GitHub-аккаунта или репозитория остаётся риском; перед полностью
автоматическим production-обновлением следует добавить проверку подписанного
тега или provenance attestation.

## Windows Desktop

Desktop-клиент использует GitHub Releases, сверяет закреплённый репозиторий,
версию, имя asset, размер и SHA-256. Для подписанных сборок дополнительно
проверяется fingerprint Authenticode-сертификата. SHA-256, опубликованный в том
же unsigned-релизе, обнаруживает повреждение, но сам по себе не подтверждает
издателя. Схема выпуска, каналы stable/preview и ротация сертификата описаны в
[desktop-updates.md](desktop-updates.md).

## После обновления

1. Проверьте статус systemd/desktop-процесса и версию из `VERSION`.
2. Изучите статус updater и журнал на наличие пропущенной миграции.
3. Выполните вход, откройте текущую и архивную кампании.
4. Проверьте импорт, предпросмотр, сверку приказа и экспорт на тестовых данных.
5. Убедитесь, что резервная копия открывается и проходит `PRAGMA quick_check`.
6. При ошибке не редактируйте production-БД вручную: остановите приложение,
   сохраните forensic-копию и восстановитесь по проверенной инструкции.

Перед публикацией нового релиза используйте [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md)
и запускайте `pip-audit` отдельно для production- и desktop-lock-файлов.
