## Ручная чистка истории — выполнять только при подтверждённой утечке

Ни одна команда ниже не выполнялась. Перед применением нужен отдельный backup, окно обслуживания и согласование со всеми владельцами клонов.

```bash
# Повторная проверка специализированным сканером после его установки.
gitleaks detect --source . --log-opts="--all" --redact

# Полностью удалить подтверждённый чувствительный файл из истории.
git filter-repo --path '<sensitive-path>' --invert-paths --force

# Заменить подтверждённый секрет по подготовленному локальному файлу правил.
git filter-repo --replace-text '<local-replacements-file>' --force

# После проверки переписанной копии владелец репозитория отдельно координирует
# принудительную публикацию веток/тегов и повторное клонирование у участников.
```

Не следует выполнять `filter-repo`, rebase или force-push в рамках этой ветки аудита.

## Ротация секретов — порядок действий

1. Сначала отозвать скомпрометированный ключ/токен у провайдера.
2. Создать новый credential с минимальными правами и ограниченным сроком.
3. Обновить секрет в защищённом хранилище или локальном `.env`, не в Git.
4. Перезапустить зависимые сервисы и завершить старые сессии, если применимо.
5. Проверить audit-логи провайдера за период возможной компрометации.
6. Только после ротации очищать историю и координировать обновление клонов.

## Остаточные ограничения

- Регулярные выражения не заменяют специализированный entropy/credential scanner; в CI будет добавлен `gitleaks`.
- Визуальная проверка изображений не является OCR-анализом, но все скриншоты имеют тестовое/пустое содержимое.
- Публичный security-контакт должен быть подтверждён владельцем проекта перед релизом документации.
